# Versioning and v1 readiness

Choose bitbones release versions from user-visible compatibility changes and verified upgrade behavior. Read this policy before recommending a version, changing the app version, or preparing a release.

bitbones is an application, with web, desktop, and Android distributions. Its version is independent of the Bitsocial protocol, PKC, and React hooks versions. [package.json](../../package.json) is the source for the app version; it marks the project private, so this is not an npm library release policy.

## Compatibility scope

Preserve supported usage within a release line: existing accounts and local data, settings, account import/export, documented hash routes, supported platforms, and integrations that consume release artifacts or the signed release manifest. Internal component structure and incidental visual details are not stable APIs. A layout improvement is not automatically a breaking change; removing a supported workflow, invalidating saved data, or requiring a user migration is.

Dependency upgrades need the same assessment. A major dependency version does not automatically require a major app version, and a dependency patch does not prove the app remains compatible. Check the effects on the installed app, supported environments, stored data, and protocol behavior.

## Choosing the number

Versions use `major.minor.patch`. Before `1.0.0`, the following rules are this repository's compatibility policy: preserve supported usage within each `0.y.x` line and announce intentional breaks with a new minor version.

| Release contents | Before `1.0.0` (`0.y.z`, with `y >= 1`) | From `1.0.0` onward |
| --- | --- | --- |
| Only docs, tests, or agent workflow changes, with no support-policy change or distributable correction | Usually no app release | Usually no app release |
| Compatible bug fixes, performance improvements, or dependency/packaging maintenance | Patch: `0.y.(z+1)` | Patch: `x.y.(z+1)` |
| Small compatible inspection feature or UI addition | Patch allowed; describe the addition | Minor: `x.(y+1).0` |
| Substantial compatible feature milestone | Minor: `0.(y+1).0` | Minor: `x.(y+1).0` |
| Deprecating supported behavior while keeping it working | Minor, with migration guidance | Minor, with migration guidance |
| Intentional break to supported usage, including platform requirements or data formats without transparent migration | Minor, with migration guidance | Major: `(x+1).0.0`, with migration guidance |
| Stable compatibility commitment with readiness criteria satisfied | `1.0.0` | Continue the stable rules above |

Use the highest required bump across the complete release, not just its commit prefixes. A documentation correction that must ship inside an artifact can justify a patch. A security or correctness fix to unintended behavior can also be a patch; explain any user impact instead of hiding it under a maintenance label.

There is no calendar deadline or feature count forcing `0.2.0` or `1.0.0`. Use a new minor for a meaningful milestone or compatibility boundary, and `1.0.0` when the app's supported behavior can be maintained compatibly. Dependencies do not need to reach v1 first. Leave existing release versions intact.

## Before recommending or preparing a release

1. Establish the target checkout/commit and actual published baseline. Inspect the manifest, reachable tags, and GitHub releases with `gh`; a local version or tag alone does not prove an artifact shipped. If remote evidence is unavailable, state that the recommendation is provisional.
2. Review the complete diff from that baseline, including dependencies, stored data, routes, platform support, and release integration changes. Identify any migration and verify affected upgrade paths.
3. Recommend an exact version with its compatibility reason, verification evidence, and remaining limits. Respect an explicitly requested version; explain any policy conflict rather than silently substituting another number.
4. For authorized preparation, use the [release skill](../../.agents/skills/release/SKILL.md) and [verification playbook](verification.md). Update the version, synchronize `yarn.lock` with `corepack yarn install`, generate and review `CHANGELOG.md` with `yarn changelog`, and verify the final state. Review the refreshed vendored lists after a build.

A version recommendation or documentation change does not authorize a commit, tag, push, or publication. Carry existing authorization through the requested release steps without adding extra approval gates.

## Release mechanics and constraints

The executable source of truth is [.github/workflows/release.yml](../../.github/workflows/release.yml), with release notes generated by [scripts/release-body.js](../../scripts/release-body.js).

- Pushing a `v*` tag triggers the release workflow. Use an exact `vX.Y.Z` tag matching `package.json`; preflight rejects a mismatch. Pushing `master` runs CI but does not trigger this release workflow. Push only the explicitly authorized branch/tag.
- To retry an existing tag after a workflow-only repair, dispatch `release.yml` from `master` with `release_tag` set to that tag. Preflight resolves the tag once; every job builds that commit, which the manifest records. This uses the repaired workflow without moving the tag or substituting untagged application source; publication still requires authorization.
- Linux, macOS, Windows, and Android jobs build artifacts, then one final job creates the GitHub release after all four succeed. The Linux job also produces the static HTML archive and signs the release manifest. Android signing is optional in the current workflow: missing signing credentials produce an unsigned APK, which is not an installable signed release. Check the actual artifacts before reporting publication complete.
- Android currently derives `versionCode` as `major * 10000 + minor * 100 + patch`. Confirm it is greater than every previously distributed Android build. Minor or patch values reaching 100 can collide with another version; change the encoding with an upgrade plan before reaching that boundary.
- Prereleases need deliberate workflow support. The current Android encoding discards a prerelease suffix, and the GitHub release step does not set the prerelease flag. Do not publish an `-rc` tag through this workflow as if it already provides a separate prerelease channel.

Verify the workflow run, tag/commit, complete asset set, versions, signatures, and affected installation/upgrade paths before calling a release complete. A successful build alone does not establish that existing users can upgrade.

## V1 readiness

These are acceptance criteria, not a completed runtime audit or a list of confirmed defects. Before recommending `1.0.0`, record dated evidence for the actual candidate revision and any explicitly accepted limits:

- **Defined support:** document supported browsers, operating systems/architectures, and integration contracts, then verify the promised environments. Do not infer a support range solely from CI runner names.
- **Safe upgrades:** verify existing accounts, settings, subscriptions, local publication history, and import/export across an upgrade from the published baseline. Document migrations and recovery steps where required.
- **Reliable core flows:** verify feeds, communities, posts/replies, account switching, publishing/challenges, and the inspector, `/stats`, and `/log`, including loading, empty, error, and recovery behavior.
- **Trustworthy diagnostics:** hook calls and displayed state match the installed hooks/PKC behavior. Check that logs, inspectors, and exported diagnostics do not expose secrets; review relevant dependency/security findings.
- **Distributable releases:** verify web/static archives, desktop packages, Android signing and upgrade identity, and the release manifest with their actual consumers. Confirm an installable artifact for each promised platform.
- **Repeatable evidence:** pass the applicable source, browser, performance, and packaging checks; add regression coverage for readiness fixes. Record the commit, commands or CI run, outcomes, and remaining gaps so another contributor can reproduce the result.

Track concrete readiness work in the existing issue backlog and link its verification evidence. A compatible `0.y.x` fix can ship while broader v1 work remains. V1 does not require every feature, zero bugs, or a coverage percentage; it requires a precise support promise backed by evidence for the release candidate.
